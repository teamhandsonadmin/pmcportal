**TL;DR**: PMC Portal is a construction-project scheduling and tracking system for a
sub-contracted trade-work operation. A Next.js/Prisma/Postgres (Supabase-hosted) admin web app
(`admin-web`) is the operational core — tracking projects, trade "Works," individual tasks with a
5-category external-approval checklist plus independent cross-trade dependencies, planned-date
scheduling with a real working-day-aware delay-propagation engine, an editable Miro-style
flowchart canvas (with both blocking "series" and non-blocking "parallel" task links), a Gantt
chart, inventory with OCR invoice intake, and site attendance. A separate Expo/React Native
mobile app (`site-engineer-app`) lets a field site engineer check in/out via GPS and submit Daily
Progress Reports with photos, entirely offline-capable via a local SQLite sync queue, writing
directly to the same Supabase Postgres database via the Supabase JS client (not through
`admin-web`'s own code at all). Admin-web and the mobile app are two independent clients of one
shared database — most of the admin app's own tables have no meaningful Supabase Row-Level
Security, while the tables the mobile app writes to are only reachable at all because RLS is
currently **disabled** on them (confirmed live, see §6/§8) — a fact worth treating as load-bearing,
not incidental.

## 1. Project Overview

**What it is**: a scheduling and progress-tracking system for a construction project run through
sub-contracted trades ("Works" — HVAC, Electrical, Plumbing, Civil, Flooring, False Ceiling,
Carpentry, POP, Waterproofing, Fabrication, Landscaping, Painting, Modular Furniture, Aluminium
Doors & Windows, Glass & Mirrors, Lighting Vendor — 16 Works exist in the real seeded dataset).
Each Work breaks down into individual **Tasks**, each of which is gated by a 6-category
external-party approval checklist (architect / client / consultant / contractor / inspector /
procurement) *and*, independently, by cross-trade **task dependencies** (a task can require
another task — possibly a different trade — to reach `completed` first).

**Who uses it** (inferred from the `UserRole` enum and route structure, not from any explicit
product-requirements doc found in the repo):
- **`admin`** and **`senior_site_engineer`** — functionally identical in terms of route access
  (see §6) — use the full back office (`admin-web`'s `(app)` route group): projects, works, tasks,
  the flowchart, Gantt, inventory, attendance review, calendar/holidays, user access management.
- **`site_engineer`** — a field user. On the web side, redirected to a still-mostly-mockup route
  group (`(site-engineer)`, see §5/§8). The *real* site-engineer experience is the separate mobile
  app: GPS attendance check-in/out and Daily Progress Report submission with photos, both
  offline-capable.
- **`client`** — an external client user scoped to exactly one project via
  `UserProfile.clientProjectId`, with access to nothing except a minimal draft-sequence canvas
  (`(client)` route group) — see §5.

**In short**: this has grown from what was likely a simple task-checklist tracker into a real
scheduling system with dependency-aware delay math, two visualization surfaces (flowchart +
Gantt), inventory/OCR, GPS attendance, and mobile daily-progress reporting — sitting alongside
several still-unbuilt back-office pages (Reports, Score Cards, Documents, admin-side DPR, Site
Photos, Project Health) that remain hardcoded UI mockups (§5, §8).

### The Flowchart, in detail

`/works/flowchart`, backed by `lib/data/works.ts`'s `getWorksData()` (a `force-dynamic` Server
Component data loader, no caching — every navigation re-queries fresh) and rendered by
`components/tasks/TaskDependencyGraph.tsx` (~1,500 lines, the single most complex client component
in the app).

**Data model**: `getWorksData()` fetches `HvacTask` (with `dependencyItems`/`work` included),
`Work`, `UserProfile`, `TaskDependency` (→ `edges`), `TaskParallelLink` (→ `parallelEdges`,
explicitly never mixed into the prerequisite-count/stats computation), and the 12 most recent
`ActivityLog` rows — all in one `Promise.all`. Per-task `prerequisiteCount`/
`prerequisiteCompletedCount` (the "X of Y done" convergence badge) is derived purely from the
`TaskDependency` set, never from parallel links.

**Rendering — two link types, one geometry**:
- **Series (blocking)** — solid orange/indigo, arrowhead, created via the "Connect" toolbar tool
  (click-tool-then-click-two-nodes). Writes a `TaskDependency` row (cycle-checked via
  `wouldCreateCycle()`), and gates `updateTaskStatus`'s `→ in_progress` transition.
  `layoutWithDagre()` feeds these edges into dagre for rank computation.
- **Parallel (non-blocking)** — dashed green, no arrowhead (an arrow would wrongly imply order),
  created via a second "Parallel" toolbar tool with the identical click-two-nodes interaction.
  Writes a `TaskParallelLink` row (symmetric — checked in both `(A,B)`/`(B,A)` orderings before
  insert). **Deliberately excluded from dagre's rank computation** (a parallel link has no
  before/after), but still rendered as a line between wherever its two nodes land.
- Both link types render through one shared `FloatingEdge` component: it reads each node's live
  position/dimensions via React Flow's `useInternalNode()` and computes where the straight line
  between the two node centers crosses each node's own rectangular boundary — so the line stays
  perfectly straight (horizontal/vertical/diagonal) regardless of whether the two nodes end up
  stacked, side-by-side, or anywhere in between, including mid-drag. This replaced an earlier
  design that used dagre's own pre-computed waypoints for auto-laid-out edges and a fixed
  Top/Bottom React Flow handle for manually-dragged ones — that split produced a visibly bent
  "staircase" line whenever a dragged node ended up beside (rather than above/below) its neighbor.

**Positioning**: dagre auto-layout (`rankdir: 'TB', nodesep: 56, ranksep: 90`) by default; dragging
a node persists `manualPositionX`/`manualPositionY` (via `updateTaskManualPosition`), and the
canvas thereafter renders that node at its stored manual position instead of its dagre-computed
one. New-node placement (`findClearPosition()`) nudges diagonally in 40px steps to avoid
overlapping an existing node's bounding box. **Reset Layout** (top-right toolbar button, typed
confirmation) calls `resetManualPositions()` to null out every currently-visible task's manual
position, then immediately re-runs `layoutWithDagre()` client-side with an empty manual-positions
map — producing a clean, fully deterministic auto-layout (re-running it twice on the same graph
produces byte-identical positions).

**Bulk "Delete All Tasks"**: a two-stage flow (`BulkDeleteDialog.tsx`) — Stage 1 shows a live count
of what would be deleted (task/checklist-item/dependency-link counts, re-queried fresh each time
the dialog opens); Stage 2 requires typing either the exact project name (scoped delete) or the
literal phrase `"DELETE ALL TASKS"` (unscoped, all-projects delete) before the button even enables,
re-checked server-side too. This is a **genuine, permanent** `prisma.hvacTask.deleteMany()` — see
§8 for the real data-loss incident history around this exact feature and why soft-delete was tried
then reverted.

Toolbar tools, in order (each now has a hover tooltip, built via a new `components/ui/tooltip.tsx`
on top of `@base-ui/react`'s Tooltip primitive): **Select** → **Add task** → **Connect** (series) →
**Parallel** (non-blocking) → **Group by trade** → divider → **Lock/Unlock canvas**. A separate
top-right utility area has **Reset Layout** and a light/dark board theme toggle. A small
always-visible legend (bottom-left of the canvas) shows both line styles with a one-line label
each. Planned-date range is shown as a small yellow-highlighted pill floating just above each task
card (zoom-gated — hidden below 0.5x zoom, since the existing 10-12px card text is already close
to illegible past that point).

### The Delay Propagation Engine

`lib/utils/delay-engine.ts`'s `computeProjectDelays(tasks, dependencies, blockedDates)` — a pure,
deterministic function (topological sort via Kahn's algorithm with a lexicographic tie-break, no
I/O, no wall-clock dependence). Per task, in topological order: completed tasks use
`actualEndDate ?? dueDate ?? plannedStartDate` as ground truth (falling back progressively, since
no completed task in the real dataset currently has an `actualEndDate` — there's no capture UI
anywhere for it); non-completed tasks project a start date from the latest of their own planned
start and one working day after each prerequisite's projected finish. Produces, per task:
`inheritedDelayDays`, `ownDelayDays`, `totalDelayDays`, and the `drivingPrerequisiteTaskId`. All
math is in working days (Sundays + `Holiday` rows excluded). A task with no planned dates and no
grounded prerequisite is tracked as "ungrounded" and can't push a downstream task's start or be
blamed as a driving prerequisite — added after testing against real seeded data showed long chains
of never-scheduled tasks fabricating meaningless delay figures. Surfaced today only on the task
overview page's "Schedule Impact" panel (via `lib/data/delay-engine.ts`'s
`getTaskScheduleImpact()`, also exposed as a server action in `app/actions/schedule-impact.ts`) —
no dashboard-wide rollup, no Gantt integration (§8).

### Mobile app (site-engineer-app)

Two real, offline-capable features, both queued through one local SQLite sync engine
(`lib/sync/`): **Attendance** (GPS check-in/out with haversine distance-from-site + mock-location
flagging) and **Daily Progress Report** (project/task selection, work details, photos). Sync
design: a `sync_queue` table (`pending`/`syncing`/`synced`/`failed`), processed strictly
sequentially (never parallel), exponential backoff (1s base, 30s cap, 5 max retries before a row
is marked permanently `failed`), triggered by connectivity-change/app-foreground events (no
polling). The DPR handler is multi-step and resumable: report row insert → optional SFT entry →
per-photo upload (each photo's local URI queued, uploaded to Supabase Storage's private
`dpr-photos` bucket at sync time, `daily_progress_report_photos` row inserted once the upload
succeeds) — a retry after partial failure only redoes the steps that didn't finish. No task/work
list screen exists in the mobile app at all; `home.tsx` is a placeholder with no real content.

## 6. Authentication & Authorization

**Request flow**: `proxy.ts` (this Next.js version's `middleware.ts` equivalent — file renamed per
`AGENTS.md`'s breaking-changes warning) runs on every route except static assets. It builds a
cookie-bound Supabase SSR client, calls `supabase.auth.getUser()` to validate the session against
Supabase Auth, and — if valid — reads a separate `user_role` cookie (set once at login, **never
re-verified against the database per request**) to route into one of three buckets: `site_engineer`
→ `/site-engineer/*`, `client` → `/client/*`, or everyone else (`admin`/`senior_site_engineer`,
treated **identically** — no distinct enforcement between the two anywhere found) → everything
outside those two prefixes. A scoped-role user hitting the wrong prefix is redirected to their own
home, not just blocked.

**Login** (`app/auth/callback/route.ts`, the only real HTTP route handler in the app): signs in via
`supabase.auth.signInWithPassword`, then resolves the role by looking up the email against
`UserProfile` (**not** by Supabase user id — there is no FK between `auth.users` and
`UserProfile.id`), falling back to `user_metadata.role ?? 'admin'` if no profile row is found. Sets
the `httpOnly`, 7-day `user_role` cookie that `proxy.ts` later reads.

**Server Action-level enforcement — the real gap**: with exactly one exception, **no Server Action
in admin-web checks the calling user's session or role at all** — every action trusts whatever ids
are passed to it. The one exception is `lib/auth/current-client.ts`'s `getCurrentClientProfile()`,
used only by the client draft-sequence actions: it independently re-derives the caller's identity
(Supabase session → email → `UserProfile` → confirms `role === 'client'` → returns their
`clientProjectId`), specifically because a `client` user must not be able to reach another
project's draft by guessing an id. This is a real, existing characteristic of the app's security
posture, not a recently-introduced bug.

**Row-Level Security — confirmed live, not just inferred from code**: `admin-web` connects via a
raw `pg` connection (Prisma + `@prisma/adapter-pg`), which **completely bypasses Supabase's
PostgREST/RLS layer** — RLS has zero effect on anything admin-web itself does, and
`supabase/schema.sql`'s own header comment says as much. But the **mobile app** talks to the same
Postgres database entirely through the Supabase JS client (PostgREST), meaning RLS *is* the only
access-control layer for everything it reads/writes. Direct database introspection this pass
(`psql`, not inference) found:
- `user_profiles`, `attendance_records`, `daily_progress_reports`, `daily_progress_report_photos`
  all have **`relrowsecurity = false`** — RLS is **disabled** on every table the mobile app reads
  from or writes to, with **zero policies defined** on any of them (`pg_policies` returns 0 rows
  for all four). This is why mobile writes succeed today — not because a correct policy permits
  them, but because there is no restriction at all once a request authenticates as any Supabase
  role with table grants.
- `storage.objects` **does** have RLS enabled, with exactly one real policy:
  `"authenticated users can upload dpr photos"` (INSERT, `authenticated` role, scoped to the
  `dpr-photos` bucket). No SELECT/UPDATE/DELETE policy exists on it — reading a photo back requires
  a signed URL minted server-side by admin-web's service-role client, not direct client access.
  Both `dpr-photos` and `inventory-documents` buckets are private (`public: false`), 10MB cap,
  JPEG/PNG only.

This resolves what the previous summary flagged as an open question ("this needs a direct check
against the live Supabase project") — the check has now been done directly.

## 8. Known Issues / Current Bugs

**The `findMany` crash — root cause confirmed, already fixed.** The prompt that generated this
document specifically named `TypeError: Cannot read properties of undefined (reading 'findMany')`
at `lib/data/works.ts:40` (`prisma.taskParallelLink.findMany`), triggered from
`app/(app)/works/flowchart/page.tsx:14`. Investigated directly: the schema and generated Prisma
client are in sync (`TaskParallelLink` exists in both, `npx prisma generate` had already been run
after the model was added). The actual cause was the Fast-Refresh-surviving Prisma singleton
(§7) — a `next dev` process that had been running since *before* `TaskParallelLink` existed in the
schema was still serving a stale client object with no `taskParallelLink` delegate at all,
independent of the source files being correct. **Fixed by killing and restarting the dev server**;
confirmed resolved (`getWorksData()` and the flowchart page both work correctly since). No code
change was needed or made — this is an environment-state issue, not a bug in `works.ts` or the
schema.

**Other real, currently-open items**:
- **Actual dates (`actualStartDate`/`actualEndDate`) have no capture UI anywhere.** Schema columns
  exist; nothing reads or writes them. A deliberate, explicit gap pending a decision on *how*
  they'd be captured (admin manual entry vs. a future mobile screen) — until resolved, the delay
  engine's "ground truth" for completed tasks is entirely proxied by `dueDate`.
- **Dashboard-wide delay rollup and lead-time alerts are not built.** The delay engine computes
  real per-task numbers; nothing aggregates them project-wide or proactively notifies anyone.
- **Client draft → real task conversion and any admin approval workflow do not exist.** A client
  can save a draft; no admin UI shows or reviews it.
- **Cross-Work dependency arrows don't render on the Gantt chart** (charting-library limitation —
  one chart instance per Work, an instance can only draw an arrow between bars it renders itself).
  Roughly half of all real dependency edges are cross-Work and simply have no Gantt arrow today.
- **The `(site-engineer)` web route group is entirely mockup** — zero Prisma calls in any of its
  three pages. The real site-engineer experience is the separate mobile app.
- **Several admin pages remain hardcoded mockups**: Reports, Score Cards, admin Alerts, Documents,
  Site Photos, Project Health.
- **`SUPABASE_SERVICE_ROLE_KEY`'s actual value has never been re-verified across multiple document
  passes** — a much earlier changelog flagged it as possibly duplicating the anon key (which would
  silently break Inventory OCR's Storage upload and DPR photo signed-URL generation). No session
  writing these docs has inspected the actual secret value (by design — values are never read for
  documentation purposes). If Inventory OCR uploads or DPR photo galleries are visibly broken,
  this is the first thing to check, with real credentials, outside of a documentation pass.
- **RLS is disabled on every table the mobile app depends on** (§6) — this is what currently makes
  mobile writes work at all, but it also means there is effectively no access control on
  `user_profiles`/`attendance_records`/`daily_progress_reports`/`daily_progress_report_photos`
  beyond whatever Supabase role-level grants exist. Worth a deliberate security decision (add real
  RLS policies vs. consciously accept the current open state), not an oversight to silently fix.
- **A known data-quality issue in the seeded reference dataset**: at least one task previously had
  an inverted planned-date pair (`plannedStartDate` after `dueDate`); `validateTaskDates()` rejects
  that combination for anything entered through the UI today, but any pre-existing bad rows
  wouldn't be caught retroactively. The flowchart/Gantt layout logic both now defensively clamp
  against `start > end` regardless.
- **`expo-file-system` is not supported on web** — confirmed in the installed package's own web
  shim (`console.warn('expo-file-system is not supported on web')`, repeated across every method).
  Combined with a separate, unrelated constraint (`expo-sqlite`'s web target needs
  cross-origin-isolation headers that Expo Router's own dev server doesn't apply without a custom
  proxy script, `scripts/web-dev-proxy.js`, or every local DB write silently hangs forever) — **DPR
  photo sync is effectively non-functional if the mobile app is ever run via a plain browser tab**
  instead of a native build or the COI-proxy dev script. This is an expected, documented platform
  limitation, not a bug to fix — the app is designed for native use.
- **A previously-tried soft-delete safety net for bulk "Delete All Tasks" was built, then
  deliberately reverted** (see §9) after real, repeated data loss showed the safety net didn't
  actually prevent the failure mode it was meant to catch. Current behavior is a genuine, permanent
  delete gated only by the typed-confirmation phrase — this is the accepted, current design, not a
  regression.
