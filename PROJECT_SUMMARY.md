## 1. Project Overview

**What it is:** "PMC Portal" is a construction / Project Management Consultancy (PMC) workflow
management web app. It targets a construction company running multiple building projects
(villas, apartment blocks) that need to track: sub-contracted trade work ("Works" like HVAC,
Electrical, Plumbing, Civil, Flooring), individual tasks within each work, and a **dependency
checklist workflow** that gates when a task can start, based on approvals/inputs from five
external parties: **architect, client, consultant, contractor, inspector**.

**Primary users / roles:**
- **Admin** / **senior_site_engineer** — full back-office access: projects, works, tasks,
  dependency templates, user/access management, reports, dashboards.
- **site_engineer** — a restricted, separate UI (`/site-engineer/*`) intended for field engineers
  to view assigned tasks, submit Daily Progress Reports (DPR), and see personal alerts.

**Core domain workflow (the one fully-implemented feature):**
1. An admin creates a **Project** → adds **Works** (trade disciplines, e.g. `HVAC`, `ELEC`) → adds
   **HVAC Tasks** under a Work.
2. Every new task is auto-seeded with a seeded list of **dependency checklist items**, one set
   per category (architect/client/consultant/contractor/inspector), 5 mandatory categories total.
3. As each checklist item is marked `delivered` / `not_required`, a **Postgres trigger**
   recalculates the task's status automatically: `draft` → `blocked` → `ready`.
4. Once `ready`, a human explicitly transitions the task through `in_progress` → `on_hold` /
   `completed` via server actions (these transitions are NOT automatic).
5. All status changes, checklist updates, comments, and task creation are recorded to an
   `activity_log` table and surfaced as activity feeds/timelines.

### Routing organization (App Router, all under `app/`)

Three route groups branch from the root, selected by the `proxy.ts` guard (see §5):

- **`(auth)`** → `/login` — public, no sidebar shell.
- **`(app)`** → the main admin/senior-engineer shell, wrapped by `SidebarLayout`. Routes:
  `/projects`, `/projects/new`, `/projects/[projectId]`, `/projects/[projectId]/works/new`,
  `/works`, `/works/new`, `/works/[workId]`, `/works/[workId]/new`, `/works/workspace` (empty
  dir, no route), `/hvac` (dependency **template** admin, despite the name), `/hvac/new`
  (redirects to `/works`), `/hvac/[taskId]` (+ nested `overview`, `dependencies`, `activity`),
  `/inventory`, `/inventory/new`, `/inventory/[itemId]`, `/inventory/upload` (added — see
  Changelog note below), `/access`, `/alerts`, `/attendance`, `/calendar`, `/documents`, `/dpr`,
  `/photos`, `/project-health`, `/reports`, `/scorecards`.
- **`(site-engineer)`** → wrapped by `SiteEngineerSidebarLayout`. Routes: `/site-engineer/works`,
  `/site-engineer/dpr`, `/site-engineer/alerts`.

Root `/` (`app/page.tsx`) unconditionally `redirect()`s to `/hvac`.

### Server Actions vs API routes

- **There are no working REST/API route handlers** for application data. `app/api/hvac/stats/`
  exists as an empty folder with no `route.ts` — a leftover scaffold.
- The only actual route handler is `app/auth/callback/route.ts` (`POST`), which performs the
  login form submission (see §5).
- All reads happen via **Prisma calls directly inside React Server Components** (`page.tsx`
  files call `prisma.*` at module/render time, no fetch layer).
- All writes happen via **Next.js Server Actions** (`'use server'` files) under `app/actions/`:
  `activity.ts`, `dependencies.ts`, `dependency-templates.ts`, `holidays.ts`, `projects.ts`,
  `users.ts`, `works.ts`, `hvac-tasks.ts`, and (added 2026-07-08) `sft.ts`, `inventory.ts`,
  `inventory-ocr.ts`. These are called from client components via `useActionState` /
  `useTransition` and typically `revalidatePath()` the relevant routes.

## 3. Data Model

Source of truth: `prisma/schema.prisma` (PostgreSQL). Prisma client is generated to a custom
path, `lib/generated/prisma`, and is gitignored. Table/column names use `@map`/`@@map` to snake_case.

### Enums
- **`UserRole`**: `admin` | `senior_site_engineer` | `site_engineer`
- **`UserStatus`**: `active` | `invited` | `disabled`
- **`TaskStatus`**: `draft` | `ready` | `in_progress` | `on_hold` | `blocked` | `completed`
- **`DependencyCategory`**: `architect` | `client` | `consultant` | `contractor` | `inspector`
- **`CompletionStatus`**: `pending` | `delivered` | `not_required`
- **`InventoryUnit`** (added 2026-07-08): `PCS` | `KG` | `TON` | `BAG` | `LITRE` | `SQFT` |
  `CUBIC_M` | `BOX` | `ROLL` | `OTHER` — **note**: UPPER_CASE, unlike every enum above (kept as
  originally specified rather than silently normalized to the file's lowercase convention)
- **`InventoryTransactionType`** (added 2026-07-08): `IN` | `OUT` | `ADJUSTMENT` (same casing note)

### Relationships summary
```
Project 1──* Work 1──* HvacTask 1──* DependencyItem 1──1 DependencyCompletion
                             │                │
                             │                └──* SftProgressEntry
                             └──* ActivityLog
Project 1──* InventoryItem 1──* InventoryTransaction
UserProfile  — referenced only by loose uuid columns (assignedTo/createdBy/completedBy/userId/
               recordedBy), no Prisma-level foreign keys to UserProfile anywhere.
DependencyTemplateItem — standalone; copied into DependencyItem rows at task-creation time.
Holiday — standalone, no relations.
```

### Database-level business logic (`supabase/schema.sql`)
Not managed by Prisma — a hand-maintained SQL file applied via
`npx prisma db execute --file supabase/schema.sql`. Implements:
- `recalculate_task_status(p_task_id)` — a plpgsql function: if task status is
  `in_progress`/`on_hold`/`completed`, no-op. Otherwise, counts distinct mandatory categories on
  the task; if fewer than 5, forces `draft`. If all 5 categories have every mandatory item
  `delivered`/`not_required`, sets `ready` (from `draft`/`blocked`); otherwise sets `blocked`
  (from `draft`/`ready`).
- Trigger `trg_completion_status_recalc` on `dependency_completions` (AFTER INSERT/UPDATE OF
  status) — recalculates the owning task's status whenever a checklist item's completion changes.
- Trigger `trg_item_change_recalc` on `dependency_items` (AFTER INSERT/DELETE) — recalculates when
  checklist items themselves are added/removed (e.g. template backfill).
- Because the app connects via Prisma/`DATABASE_URL` directly to Postgres (not through
  Supabase's PostgREST layer), **Row Level Security is intentionally not used/defined** — this
  is explicitly called out in a comment in the SQL file. Auth/authorization is enforced entirely
  in the Next.js layer (proxy.ts + role cookie), not at the database level.

## 5. Auth & Permissions

**Login flow:**
1. `/login` (`app/(auth)/login/page.tsx`) is a Server Component that checks for an existing
   Supabase session (`supabase.auth.getUser()`) and redirects to `/projects` if already
   authenticated. Renders a plain HTML `<form action="/auth/callback" method="post">`.
2. Submitting posts to `app/auth/callback/route.ts` (`POST`), which:
   - Calls `supabase.auth.signInWithPassword({ email, password })`.
   - On failure, redirects back to `/login?error=Invalid email or password`.
   - On success, looks up the user's role: **first tries `prisma.userProfile.findUnique({ email })`**
     (direct DB read, bypasses Supabase RLS since Prisma connects straight to Postgres), and
     **falls back to `signInData.user.user_metadata.role`** (set manually in the Supabase Auth
     dashboard) if no `UserProfile` row exists or the Prisma call throws. Defaults to `'admin'`
     if neither source yields a role.
   - Redirects to `/site-engineer/works` (role `site_engineer`) or `/projects` (everyone else).
   - Sets an **httpOnly cookie `user_role`** (7-day maxAge, `sameSite: lax`) so the route
     guard doesn't need a DB round-trip on every request.

**Route guard (`proxy.ts`, Next.js 16's renamed `middleware.ts`):**
- Runs on every request except static assets (`_next/static`, `_next/image`, `favicon.ico`,
  image extensions) per its `matcher`.
- Always allows `/login*` and `/auth/*`.
- If no Supabase session user → redirect to `/login`.
- Reads `role` from the `user_role` cookie (defaults to `'admin'` if the cookie is missing —
  i.e., a logged-in user with no cookie is treated as admin, not blocked).
- If role is `site_engineer` and the path isn't under `/site-engineer` → redirect to
  `/site-engineer/works`.
- If role is NOT `site_engineer` and the path IS under `/site-engineer` → redirect to `/projects`.

**Roles:** `admin`, `senior_site_engineer`, `site_engineer` (Prisma enum `UserRole`). In practice
the proxy guard only distinguishes `site_engineer` vs. everyone-else — `admin` and
`senior_site_engineer` currently have identical route access; there is no page-level
permission check that further separates admin-only actions (e.g. `/access` user management is
reachable by any non-site-engineer role).

**Session/identity gap:** Nowhere in the read codebase does a page or component read the actual
signed-in user's name/email/id from the Supabase session to personalize the UI — the sidebar/
header identity blocks are hardcoded strings (see §4), and `ActivityLog.userId`,
`HvacTask.createdBy`, and `DependencyCompletion.completedBy` are never populated by any server
action. This means "who did what" is not actually tracked yet despite the schema supporting it.

**Supabase client setup:**
- `lib/supabase/client.ts` — browser client (`createBrowserClient`), used for the sidebar logout calls.
- `lib/supabase/server.ts` — server client (`createServerClient`, cookie-bound via `next/headers`).
  Falls back to placeholder URL/key constants if env vars aren't set (`https://placeholder.supabase.co`)
  so server components don't hard-crash in a misconfigured environment.

## 8. API Endpoints

There is exactly **one** HTTP route handler in the entire app. Everything else is Server
Components (reads) and Server Actions (writes) — see §2 for why.

### `POST /auth/callback`
- **File:** `app/auth/callback/route.ts`
- **Purpose:** Handles the login form submission from `/login`.
- **Request:** `multipart/form-data` (from an HTML `<form>`) with fields:
  - `email: string`
  - `password: string`
- **Response:** Always a redirect (`303 See Other`), never JSON:
  - On invalid credentials → `Location: /login?error=Invalid%20email%20or%20password`
  - On success → `Location: /projects` (admin/senior_site_engineer) or
    `Location: /site-engineer/works` (site_engineer), plus a `Set-Cookie: user_role=<role>`
    (httpOnly, `sameSite=lax`, `path=/`, `maxAge=604800`).
